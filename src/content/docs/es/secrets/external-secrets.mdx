Las aplicaciones necesitan contraseñas, claves de API y tokens. No pueden ir en git, ni siquiera
en un repositorio privado, pero ArgoCD solo aplica lo que está en git. Este capítulo lo resuelve:
los secretos viven en **Bitwarden Secrets Manager**, y **External Secrets** los copia al clúster
como Secrets de Kubernetes. Git solo guarda *qué* secreto necesita una aplicación, nunca su valor.
Al terminar tendrás:
- un proyecto de Bitwarden para el clúster, y una **cuenta de máquina** que puede leerlo,
- **External Secrets** y **cert-manager** instalados por ArgoCD desde tu repositorio,
- un **ClusterSecretStore** que puede usar cualquier namespace,
- un secreto de demostración que sigue a Bitwarden cuando lo cambias allí.

<Aside type="tip" title="Hazlo con un agente de IA">
Este capítulo tiene una skill para agentes, `secrets`. Consulta [Usar con un agente de IA](/es/start-here/agents/).
</Aside>

**Probado con:** External Secrets 2.14.0, cert-manager 1.21.3, Bitwarden SDK server 0.6.0, sobre
k3s v1.37.2+k3s1 con ArgoCD 3.6.1.

## Antes, unas ideas

### Las piezas
```text
Bitwarden Secrets Manager                       tu clúster
┌──────────────────────┐  cuenta de máquina  ┌────────────────────────────────────────────┐
│ proyecto "lab-1"     │◀── token de acceso ──│ ClusterSecretStore "bitwarden"             │
│   demo-message = …   │                      │   ▲                                        │
│   db-password  = …   │                      │ ExternalSecret: "necesito demo-message"    │
└──────────────────────┘                      │   ▼                                        │
                                              │ Secret "demo" (lo que lee la aplicación)   │
                                              └────────────────────────────────────────────┘
```

- Un **proyecto** de Bitwarden Secrets Manager guarda los secretos del clúster. Una **cuenta de
  máquina** es un usuario no humano con acceso de lectura a ese proyecto, y su **token de acceso**
  es como entra el clúster.
- Un **ClusterSecretStore** dice «así se llega a Bitwarden». Lo escribes una vez.
- Un **ExternalSecret** dice «crea un Secret de Kubernetes con estos valores del store». Nombra
  secretos, así que es seguro en git, y cada aplicación tiene el suyo.
- External Secrets consulta Bitwarden de forma periódica y mantiene cada Secret al día.

### El único secreto que creas a mano
El clúster necesita el token de la cuenta de máquina *antes* de poder leer nada de Bitwarden, así
que ese token no puede venir de Bitwarden. Lo pones en el clúster una vez, con un script que te lo
pide con entrada oculta. Todos los demás secretos vienen de Bitwarden.

### Por qué aparece cert-manager aquí
External Secrets habla con Bitwarden a través de un pequeño ayudante dentro del clúster, el
**Bitwarden SDK server**, y ese ayudante solo habla HTTPS. **cert-manager** crea su certificado. El
capítulo 5 vuelve a usar cert-manager, para certificados HTTPS de verdad.

El razonamiento detrás de cada elección está en las [preguntas frecuentes](/es/start-here/faq/#capítulo-4--secretos).

## Antes de empezar

- [ ] El capítulo 3 terminado: ArgoCD gestiona el clúster desde tu repositorio, y `root` está
      `Synced`.
- [ ] Una cuenta de Bitwarden. Secrets Manager es un producto distinto del gestor de contraseñas,
      y su plan gratuito basta aquí.

## Prepáralo

<Steps>

1. **Prepara Bitwarden Secrets Manager.** En la aplicación web de Bitwarden, abre **Secrets
   Manager** desde el selector de productos. La primera vez, creas o eliges una organización para
   él. Después:
   1. **Projects → New project**, con el nombre de tu clúster, por ejemplo `lab-1`.
   2. **Secrets → New secret**: nombre `demo-message`, valor `hello from Bitwarden`, proyecto
      `lab-1`.
   3. **Machine accounts → New machine account**, llamada `lab-1`. En su pestaña **Projects**,
      añade `lab-1` con **Can read**.
   4. En la pestaña **Access tokens** de la cuenta de máquina, crea un token. Bitwarden lo muestra
      una sola vez: guárdalo en tu gestor de contraseñas como «Bitwarden SM token (lab-1)».

   Apunta dos ids. No son secretos: sin el token no dan acceso a nada.
   - El **id de la organización** está en la barra de direcciones: `…/sm/<ORGANIZATION_ID>/…`.
   - El **id del proyecto** está en la barra de direcciones al abrir el proyecto:
     `…/projects/<PROJECT_ID>/…`.

2. **Pon el token de acceso en el clúster.** Copia
   [`examples/04-secrets`](https://github.com/romansegador/homelab-guide/tree/main/examples/04-secrets)
   en tu repositorio privado, uniendo sus carpetas `apps/`, `bootstrap/` y `manifests/` con las del
   capítulo 3. Después ejecuta el script y pega el token cuando lo pida:

   ```sh title="Portátil"
   bash bootstrap/add-bitwarden-token.sh
   ```

   Va primero para que el token esté esperando cuando arranque External Secrets.

3. **Rellena tus valores y haz push.**
   - En `apps/secrets-config.yaml` y `apps/secret-demo.yaml`, sustituye `<YOUR_CONFIG_REPO_URL>`
     por la dirección SSH de tu repositorio, como en el capítulo 3.
   - En `manifests/secrets-config/cluster-secret-store.yaml`, pon `organizationID` y `projectID`.
     Si tu cuenta de Bitwarden está en la nube europea (entras en `vault.bitwarden.eu`), cambia dos
     líneas del mismo fichero: `apiURL` a `https://api.bitwarden.eu`, e `identityURL` a
     `https://identity.bitwarden.eu`. Deja `bitwardenServerSDKURL` como está: apunta al servicio
     auxiliar dentro de tu clúster.

   Haz commit y push a `main`. ArgoCD recoge los cuatro ficheros nuevos de `apps/` en 3 minutos, o
   pulsa **Refresh** en `root` en la interfaz.

4. **Míralo arrancar.** ArgoCD instala cert-manager y External Secrets, y después el certificado y
   el store. La primera sincronización del store puede fallar mientras los otros dos aún se
   instalan: ArgoCD reintenta solo. Tras unos minutos:

   ```sh title="Portátil"
   kubectl -n argocd get applications
   kubectl get clustersecretstore bitwarden
   ```

   Todas las Applications están `Synced` y `Healthy`, y el store muestra `Valid` y `READY` `True`.

</Steps>

## Compruébalo

**El secreto ha llegado:**

```sh title="Portátil"
kubectl -n secret-demo get externalsecret demo
kubectl -n secret-demo get secret demo -o jsonpath='{.data.message}' | base64 -d; echo
```

El ExternalSecret muestra `SecretSynced`, y el segundo comando imprime `hello from Bitwarden`.

**Sigue a Bitwarden.** En Bitwarden, cambia `demo-message` a `hello again`. La demostración
comprueba cada minuto, así que en menos de un minuto el segundo comando de arriba imprime
`hello again`.

**Git no guarda el valor.** Abre `manifests/secret-demo/secret-demo.yaml`: nombra `demo-message`,
y el valor no está en ninguna parte de tu repositorio.

**Quita la demostración.** Borra `apps/secret-demo.yaml` y `manifests/secret-demo/`, haz commit y
push. Tras la siguiente sincronización, el namespace `secret-demo` y su Secret han desaparecido:

```sh title="Portátil"
kubectl get namespace secret-demo
```

Dice `NotFound`. También puedes borrar `demo-message` en Bitwarden.

## Antes de seguir

- [ ] Todas las comprobaciones pasan, y la demostración está quitada.
- [ ] En tu gestor de contraseñas: el **token de acceso de Bitwarden SM**.
- [ ] Los nuevos ficheros de `apps/`, `bootstrap/` y `manifests/` con commit. No contienen valores
      secretos.

A partir de ahora, una aplicación que necesita un secreto lleva un ExternalSecret al lado en git, y
el valor va en Bitwarden. Siguiente: HTTPS y DNS privado.
