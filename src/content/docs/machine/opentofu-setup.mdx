title: Set up OpenTofu
description: Everything OpenTofu needs before it can create the machine. A limited Proxmox API token, a restricted SSH user, and an encrypted remote state.
---

import { Tabs, TabItem, Steps, Aside } from '@astrojs/starlight/components';

**Only for the as-code path.** If you'll create the VM in the Proxmox web UI, skip to
[Create the machine](/machine/create/).

OpenTofu runs on **your laptop** (or later, a CI job) and reaches Proxmox from there. Before the first
`tofu apply`, it needs four things, and none of them is root access:

| What | Why | Where it lives |
|---|---|---|
| A Proxmox **API token** with limited privileges | Creates and changes the VM through the Proxmox API | Your password manager |
| A restricted **SSH user** on Proxmox | Uploads the cloud-init file (the one thing the API can't do) | Your SSH key, in your SSH agent |
| A **bucket** for the state, plus its access keys | Keeps OpenTofu's record of what it created somewhere safer than your laptop | Keys in your password manager |
| A **state passphrase** | Encrypts the state before it leaves your laptop | Your password manager |

The reasoning behind each choice is in the [FAQ](/start-here/faq/#chapter-1--the-machine).

<Aside type="tip" title="Do it with an AI agent">
The `machine` skill covers this page too. See [Use with an AI agent](/start-here/agents/). The agent
never sees your token, keys or passphrase: you create and export those yourself.
</Aside>

<Steps>

1. **Install OpenTofu** on your laptop ([install guide](https://opentofu.org/docs/intro/install/)), then check it:

   ```sh title="Laptop"
   tofu version
   ```

   It should print `OpenTofu v1.12.x` or newer.

   <Aside>Prefer **Terraform**? The examples work with it unchanged: type `terraform` where the
   guide types `tofu`. The one exception is the state encryption in step 5. Terraform doesn't have
   it, so you'd rely on the bucket's own encryption instead.</Aside>

2. **Create a Proxmox API user and token.** It gets only the privileges it needs to manage VMs,
   not root:

   ```sh title="Proxmox host"
   pveum user add tofu@pve --comment "OpenTofu provisioning"
   pveum role add TofuProvisioner -privs "Datastore.Allocate Datastore.AllocateSpace \
     Datastore.AllocateTemplate Datastore.Audit Pool.Audit SDN.Audit SDN.Use Sys.Audit Sys.Console \
     Sys.Modify VM.Allocate VM.Audit VM.Clone VM.Config.CDROM VM.Config.CPU VM.Config.Cloudinit \
     VM.Config.Disk VM.Config.HWType VM.Config.Memory VM.Config.Network VM.Config.Options \
     VM.Console VM.GuestAgent.Audit VM.Migrate VM.PowerMgmt"
   pveum aclmod / -user tofu@pve -role TofuProvisioner
   pveum user token add tofu@pve provider --privsep 0
   ```

   The last command prints the token secret **once**. Store it in your password manager now.

   <Aside>If a later `tofu apply` fails with `Permission check failed (…, <PRIVILEGE>)`, add that
   privilege with `pveum role modify TofuProvisioner -append 1 -privs <PRIVILEGE>`. Privilege names
   changed in Proxmox 9.</Aside>

3. **Create a restricted SSH user on Proxmox.** The provider uploads the cloud-init file over SSH,
   because the Proxmox API can't upload "snippets". This Linux user can do **only** that: it may run
   two exact commands as root, and nothing else. (It's unrelated to the `tofu@pve` API user above.)

   Replace `<YOUR_SSH_PUBLIC_KEY>` with the contents of your `~/.ssh/id_ed25519.pub`. The first
   command installs `sudo`, which Proxmox doesn't ship:

   ```sh title="Proxmox host"
   apt install -y sudo
   useradd -m -s /bin/bash tofu
   install -d -m 700 -o tofu -g tofu /home/tofu/.ssh
   echo '<YOUR_SSH_PUBLIC_KEY>' > /home/tofu/.ssh/authorized_keys
   chown tofu:tofu /home/tofu/.ssh/authorized_keys && chmod 600 /home/tofu/.ssh/authorized_keys
   cat > /etc/sudoers.d/tofu <<'EOF'
   tofu ALL=(root) NOPASSWD: /usr/sbin/pvesm apiinfo
   tofu ALL=(root) NOPASSWD: /usr/bin/tee ^/var/lib/vz/snippets/[a-zA-Z0-9_][a-zA-Z0-9_.-]*$
   EOF
   chmod 440 /etc/sudoers.d/tofu && visudo -c
   ```

   The first rule is how the provider checks that sudo works. The second lets it write a file into
   the snippets folder of the `local` storage, and nowhere else. (`/var/lib/vz` is where `local`
   lives. If your snippets go to another storage, use its path from `pvesh get /storage/<name>`.)

   Check it from your laptop. The first command must list your key (it's loaded in your SSH agent).
   The second must print an `APIVER` line without asking for a password:

   ```sh title="Laptop"
   ssh-add -l
   ssh tofu@proxmox.home.example.com sudo pvesm apiinfo
   ```

   <Aside type="caution">Never widen these rules to the whole `pvesm` or `qm` commands, or to
   `tee` with a `*`. Each of those is as good as root.</Aside>

4. **Create a bucket for the state.**

   <Tabs syncKey="state-bucket">
   <TabItem label="Cloudflare R2">

   R2 is Cloudflare's S3-compatible storage. The state is a few kilobytes, far inside the free tier,
   but enabling R2 the first time asks for a payment method.

   1. In the Cloudflare dashboard, open **R2 Object Storage** and **Create bucket**. Name it
      `homelab-tofu-state` and leave the location on automatic.
   2. On the R2 overview, open **Manage API tokens → Create API token**:
      - Permissions: **Object Read & Write**.
      - Scope: **Apply to specific buckets only**, and pick `homelab-tofu-state`.
   3. Cloudflare shows an **Access Key ID** and a **Secret Access Key** once. Store both in your
      password manager.
   4. Note your **account ID**. It's part of the S3 endpoint shown in the bucket's settings:
      `https://<YOUR_CLOUDFLARE_ACCOUNT_ID>.r2.cloudflarestorage.com`. It isn't secret.

   </TabItem>
   <TabItem label="Other S3-compatible storage">

   Any S3-compatible service works: Amazon S3, Backblaze B2, or another provider. Create a private
   bucket and an access key that can read and write **only that bucket**. Note its endpoint and
   region. The example's `backend.hcl.example` shows what to change.

   Avoid a bucket hosted on the homelab itself, at least for this state. The state describes the
   machine, so it shouldn't live on that machine.

   </TabItem>
   </Tabs>

5. **Choose a state passphrase.** Generate a long random passphrase (16 characters at least) in
   your password manager and save it there.

   <Aside type="danger">Without the passphrase, the state can't be decrypted. OpenTofu then no
   longer knows it manages the VM, and you'd have to import it back by hand. Keep the passphrase
   in your password manager, not only in your head.</Aside>

6. **Know how you'll load the secrets.** Every time you run `tofu`, the shell needs the four
   values as environment variables. Type or paste them, or load them from your password manager's
   CLI. Never write them into a file in the repository:

   ```sh title="Laptop"
   export PROXMOX_VE_API_TOKEN='tofu@pve!provider=<token secret>'
   export AWS_ACCESS_KEY_ID='<bucket access key id>'
   export AWS_SECRET_ACCESS_KEY='<bucket secret access key>'
   export TF_VAR_state_passphrase='<state passphrase>'
   ```

   They last until you close that terminal.

</Steps>
